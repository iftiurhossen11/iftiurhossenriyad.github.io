Foundations of Log Analysis for Cyber Defense - 1.1 What Are Logs and Why They Matter
Introduction
In cybersecurity operations, especially from a Blue Team perspective, logs are fundamental to visibility, monitoring, and response. They represent the footprints of everything that happens in a system, application, or network. Without logging, detecting abnormal behavior or tracking malicious activity becomes nearly impossible.
A log is a timestamped record generated by a system, application, service, device, or security tool. Logs document events such as user authentications, process executions, network connections, file accesses, configuration changes, system errors, or security policy violations.
Types of Logs (by Source)
Source | Log Example | Use Case for Blue Team
Operating System (Linux) | /var/log/auth.log | SSH login attempts, sudo usage
Operating System (Windows) | Security.evtx | Logons, process creations, privilege usage
Network Devices | Firewall logs, DHCP logs | Blocked traffic, address leasing
Web Servers | Apache, Nginx access/error logs | Suspicious URIs, 404 fuzzing, directory traversal
Security Tools | EDR, antivirus, SIEM logs | Threat detections, lateral movement
Cloud Infrastructure | AWS CloudTrail, Azure Activity Log | API misuse, privilege escalation attempts
Event vs Log
* Event: A single instance or action (e.g., “User X logged in”).
* Log: The written record of an event, possibly structured (JSON) or unstructured (plaintext).
Every log contains at least a timestamp, the source/system, and the description of the event. Additional fields depend on the software/hardware generating the log.
Real Examples of Log Entries
1. Linux SSH Authentication Failure
Jun 20 18:45:32 ubuntu sshd[2541]: Failed password for root from 192.168.1.23 port 49522 ssh2
* Interpretation: The system rejected an SSH password attempt for the root user from IP 192.168.1.23.
* Use Case: Correlate multiple failed attempts to detect brute-force activity.
2. Windows Logon Event (Security.evtx, Event ID 4624)
Log Name: SecurityEvent ID: 4624Logon Type: 10Account Name: AdministratorSource Network Address: 10.0.0.14
* Interpretation: A successful Remote Desktop Protocol (RDP) login from 10.0.0.14 to the Administrator account.
* Use Case: Detection of unauthorized RDP access or lateral movement.
3. Web Server Access Log (Apache)
192.168.1.50 - - [29/Jun/2025:14:23:42 +0000] "GET /admin HTTP/1.1" 401 487
* Interpretation: Client 192.168.1.50 attempted to access a restricted area (/admin) and received a 401 Unauthorized.
* Use Case: Detecting probing or web-based brute-force against login/admin portals.
4. IDS Alert (Suricata JSON format)
{  "timestamp": "2025-06-29T16:21:00.512293Z",  "event_type": "alert",  "src_ip": "192.168.1.10",  "dest_ip": "10.10.1.23",  "alert": {    "signature": "ET SCAN Nmap -sS Syn Scan",    "severity": 2  }}
* Interpretation: Intrusion detection system identified a SYN scan likely from Nmap.
* Use Case: Alert triage, source attribution, trigger correlation in SIEM.
Why Logs Are Critical for Blue Teams
* Visibility: Logs provide insight into user activity, system changes, and potential threats.
* Forensics: In post-incident investigation, logs are often the only timeline available.
* Detection Engineering: All detection rules (e.g., in SIEM or EDR) rely on log-based patterns.
* Compliance and Auditing: Regulatory frameworks like PCI-DSS, HIPAA, and ISO 27001 require evidence of logging.
* Threat Hunting: Hypothesis-based searches through logs can reveal stealthy attackers.
Common Blue Team Use Cases Involving Logs
Use Case | Related Log Type(s)
Detect brute-force attacks | SSH logs, Event ID 4625 (Windows)
Investigate privilege abuse | Event ID 4672 (Windows), sudo logs (Linux)
Detect suspicious command execution | Event ID 4688, Sysmon, bash_history
Trace lateral movement | RDP logs, SMB connections, port scans
Identify web attack vectors | Apache/Nginx access logs, WAF logs
Monitor file access or exfil | File integrity logs, EDR telemetry
Logging Pitfalls to Avoid
* No central logging: Local logs are easily erased by attackers.
* No time sync (NTP): Event correlation becomes unreliable.
* Unstructured logging: Makes automation and parsing harder.
* Insufficient retention: Historical analysis becomes impossible.
* Too much noise: Without filtering, important signals get buried.
Logs are the foundation of security operations. Whether responding to incidents, building detections, or hunting for threats, Blue Teams depend on accurate, complete, and well-structured log data. Understanding the types of logs, their format, and their role in daily security tasks is the first step toward mastering log analysis.
Foundations of Log Analysis for Cyber Defense - 1.2 Common Log Formats and Structures
Introduction
Effective log analysis requires not only understanding what logs are, but also how they are structured. Logs come in many formats depending on their origin, such as operating systems, network devices, security tools, and web servers. A Blue Team analyst must be able to quickly identify the format of a log, parse its key fields, and extract relevant information for triage, detection, and investigation.
Logs may be structured, semi-structured, or unstructured. The format used affects how easily logs can be ingested by SIEM platforms, parsed with tools, or correlated across systems.
Log Format Categories
* Plain Text Logs
Common in Linux systems and legacy applications. These are human-readable and line-oriented but often require regular expressions or tools like grep for parsing.
* Key-Value Pair Logs
Each line contains space-separated key=value pairs. This structure allows basic parsing and filtering.
* CSV Logs
Comma-separated values, useful for exporting and analyzing in Excel or ingestion by SIEMs.
* JSON Logs
Structured logs used by modern applications and tools like Suricata, AWS CloudTrail, or Elastic Beats. Easily parsed by machines and log pipelines.
* XML Logs
Less common today but still used in legacy systems and some enterprise software.
* Binary Logs
Examples include Windows Event Logs (EVTX), which require special tools like Event Viewer or LogParser to read.
Practical Examples by Format
1. Plain Text – Linux Auth Log
Jun 30 10:12:43 server sshd[1290]: Accepted password for admin from 192.168.0.12 port 50222 ssh2
Key elements: timestamp, hostname, process (sshd), status message
Use case: Authentication success, origin IP, user identity
2. Key-Value Format – Systemd Journal Log
MESSAGE=Failed password for invalid user test from 10.1.1.5 port 50022 ssh2PRIORITY=3SYSLOG_IDENTIFIER=sshd
Use case: Useful in Red Hat-based systems using journalctl. Easier to extract specific fields.
3. CSV Format – Firewall Log Export
timestamp,src_ip,dest_ip,port,action2025-06-30 12:01:55,10.0.0.5,192.168.10.1,443,allow
Use case: Easy import into SIEM or spreadsheets for analysis of firewall behavior.
4. JSON Format – Suricata Alert
{  "timestamp": "2025-06-30T12:04:11.482Z",  "event_type": "alert",  "src_ip": "10.10.10.10",  "dest_ip": "192.168.100.5",  "alert": {    "signature": "ET SCAN Nmap Scripting Engine",    "severity": 2  }}
Use case: Structured format makes this ideal for parsing in SIEMs or log pipelines like ELK. Allows querying fields such as alert.signature or src_ip.
5. XML Format – Web Application Firewall Log
<event>  <date>2025-06-30</date>  <src_ip>172.16.0.8</src_ip>  <event_type>SQL Injection Attempt</event_type></event>
Use case: Some older or enterprise tools output XML. Requires XPath or similar methods for extraction.
6. EVTX (Binary) – Windows Event Log
Can be viewed using:
* Event Viewer GUI
* Get-WinEvent or wevtutil via PowerShell
* LogParser or SIEM agent ingestion
Example (Security.evtx, Event ID 4688):
A new process has been created.New Process Name: C:\Windows\System32\cmd.exeCreator Process: C:\Windows\explorer.exe
Use case: Detecting suspicious process execution like cmd.exe, powershell.exe, or rundll32.exe.
Field Standardization and Normalization
Since each log source has its own schema, one of the biggest challenges in centralized log analysis is normalization. This is the process of converting different log formats and fields into a common schema.
For example:
Raw Field (Vendor-specific) | Normalized Field
src_ip, source-address, ip.src | source_ip
username, user, acct | user_name
timestamp, @timestamp, time | event_time
This standardization is critical in SIEM platforms like Splunk, Elastic Security, or QRadar to build detection rules that work across multiple data sources.
Practical Considerations for Blue Teams
* Use parsing and enrichment tools like Logstash, Fluent Bit, or syslog-ng to convert and enrich log data.
* Build dashboards based on normalized fields for cross-platform visibility.
* Validate that log sources produce structured outputs whenever possible to ease correlation and search.
* Understand how your SIEM ingests and parses each log type.
Understanding log formats is a core skill for any Blue Team professional. Each source system, whether it's an operating system, firewall, or application, produces logs in its own format, and these formats directly affect how logs can be ingested, parsed, and analyzed.
Being able to recognize and work with different formats such as plaintext, JSON, CSV, and binary (like Windows EVTX) is essential for building effective detection rules, hunting threats, and conducting forensic investigations. Additionally, the process of normalizing logs across different systems ensures that security operations teams can correlate events accurately and build scalable detection logic.
Foundations of Log Analysis for Cyber Defense - 1.3 Timestamps, Timezones, and Synchronization (NTP)
Introduction
Accurate timestamps are one of the most critical components of effective log analysis. Time-based correlation is the backbone of detecting, investigating, and reconstructing security incidents. When timestamps are misaligned across different systems, analysts may misinterpret the sequence of events or completely overlook key indicators.
Ensuring that all systems use consistent and synchronized time is a fundamental practice in cybersecurity operations. This is accomplished using Network Time Protocol (NTP), which allows devices to regularly update their internal clocks from a trusted time source.
Understanding Timestamps
Most logs contain timestamps that indicate when an event occurred. However, the format, timezone, and precision of these timestamps can vary significantly depending on the source.
Common timestamp formats:
* Human-readable local time
Jun 30 14:22:432025-06-30 18:45:12
* UTC time with timezone offset
2025-06-30T18:45:12+00:002025-06-30T18:45:12Z
* Epoch/Unix time (integer value of seconds since 1970-01-01)
Timestamp: 1751372712 → Human time: 2025-06-30 18:45:12 UTC
* High-precision timestamp with milliseconds or microseconds
2025-06-30T18:45:12.783Z2025-06-30 14:22:43.154 +0200
Each of these formats may be used in different environments or tools, such as syslog, web server logs, cloud logs, or SIEM platforms.
Timezone Discrepancies in Log Analysis
Timezone misalignment is a common problem during incident investigation. For example, if a firewall logs in UTC, a Linux server logs in local time (UTC-3), and an application server logs in UTC+1, then the same event might appear to occur at three different times.
This leads to:
* Misinterpretation of event order
* Gaps in correlation logic
* Incorrect incident timelines
* False positives in detection rules
Example Scenario
Three logs from different systems, showing the same event:
Linux server (UTC-3):
Jun 30 15:12:02 sshd[2991]: Accepted password for joao from 10.0.0.10
Firewall (UTC):
2025-06-30T18:12:02Z src=10.0.0.10 dst=192.168.1.20 action=accept
Application log (UTC+1):
2025-06-30 19:12:02 user=joao login_success=true
Although all these events refer to the same authentication session, the timestamps differ by hours. Without a standardized time reference, incident correlation becomes unreliable.
Network Time Protocol (NTP)
NTP is a protocol that synchronizes system clocks with designated time servers. When implemented correctly, it ensures that all systems within an infrastructure maintain consistent time — typically synchronized to Coordinated Universal Time (UTC).
Linux Configuration
To enable and verify NTP synchronization:
sudo timedatectl set-ntp truetimedatectl status
Output Example:
Local time: Mon 2025-06-30 15:00:00 -03Universal time: Mon 2025-06-30 18:00:00 UTCNTP synchronized: yes
Windows Configuration
NTP settings are controlled via Control Panel or PowerShell:
w32tm /query /statusw32tm /resync
Best Practices:
* Use a central internal NTP server or a pool of public NTP servers.
* Avoid relying on system BIOS or hardware clocks.
* Monitor and alert on systems that deviate from expected time accuracy.
* Normalize timestamps to UTC in SIEM platforms to ensure consistent correlation.
Timestamp Normalization in Log Pipelines
Many organizations normalize timestamps at the log ingestion stage. For example, Logstash or Fluent Bit can parse and convert various timestamp formats into a standardized field like @timestamp in UTC.
Logstash Example:
filter {  date {    match => [ "log_time", "yyyy-MM-dd HH:mm:ss" ]    target => "@timestamp"    timezone => "UTC"  }}
SIEMs like Splunk or Elastic Search rely heavily on timestamp parsing for alerting, correlation, and timeline views. Incorrectly parsed or missing timestamps often cause events to be indexed out of order or excluded from detection logic.
Foundations of Log Analysis for Cyber Defense - 1.4 Log Rotation and Retention Policies
Introduction
As systems and applications run continuously, logs can grow rapidly and consume significant disk space if not properly managed. Uncontrolled log growth may lead to system instability, data loss, or inability to retain important forensic evidence. Blue Team professionals must understand and implement log rotation and retention strategies to ensure performance, availability, and security compliance.
Log rotation refers to the process of archiving, compressing, or deleting old log files after a specific time interval or when a size threshold is reached. Retention policies define how long logs should be stored and which logs are critical to preserve for auditing, detection, or investigation.
Why Log Management Is Critical
* Disk space control: Prevents logs from filling up the disk and crashing services.
* Forensic preservation: Ensures key evidence is available during an incident investigation.
* Compliance: Many frameworks (e.g., PCI-DSS, HIPAA, ISO 27001) require logs to be retained for months or years.
* Performance: Overly large log files can slow down parsing tools and SIEM ingestion.
* Alerting: Missed log rotation may indicate misconfiguration or malicious log tampering.
Log Rotation in Practice
Linux Systems
Most Linux distributions use logrotate, a utility that manages the rotation, compression, and deletion of log files. It is configured via /etc/logrotate.conf and individual files in /etc/logrotate.d/.
Example:
/var/log/auth.log {    weekly    rotate 4    compress    missingok    notifempty}
This configuration means:
* Logs are rotated weekly.
* Only 4 archives are kept.
* Old logs are compressed (e.g., .gz).
* Rotation is skipped if the file is empty.
* If the file is missing, no error is raised.
Manual Test:
sudo logrotate --debug /etc/logrotate.conf
Windows Systems
Windows Event Logs rotate automatically based on file size or overwrite policy. These settings can be changed via the Event Viewer.
Steps:
* Open Event Viewer → Right-click a log (e.g., Security) → Properties
* Set maximum log size (e.g., 200 MB)
* Choose action: Overwrite events, archive logs, or stop logging
PowerShell Check:
Get-EventLog -LogName Security | Measure-Object
Retention Policy Design
Log retention depends on multiple factors:
* Regulatory requirements
* Internal security policy
* Storage capacity
* Business risk and criticality of system
Typical Retention Guidelines:
Log Type | Recommended Retention
Authentication logs (SSH, RDP) | 180–365 days
Security logs (EDR, SIEM) | 1–3 years
Web server access logs | 90–180 days
Firewall, IDS/IPS logs | 90–365 days
Cloud API activity logs | 180–365 days
Compliance-regulated systems | 1–7 years
Retention Tools and Strategies:
* Centralize logs in SIEM or cloud storage (e.g., S3, Azure Blob)
* Implement cold storage tiers for infrequently accessed logs
* Encrypt archived logs to maintain confidentiality and integrity
* Tag logs with metadata to automate lifecycle management
Security Considerations
* Prevent unauthorized access to archived logs
* Monitor for log deletion or tampering attempts
* Ensure log forwarding continues after rotation
* Validate that logs are not truncated during compression or archiving
Log Forwarding Example (Linux rsyslog):
*.* @192.168.1.10:514
This sends all log events to a centralized syslog server.

Foundations of Log Analysis for Cyber Defense - 2.1 Linux Log Sources and Authentication Analysis
Introduction
Linux systems produce a wide variety of logs that are essential for tracking user activity, authentication attempts, privilege escalation, and system behavior. Blue Team professionals need to understand where these logs are stored, how they are structured, and how to interpret them to detect suspicious behavior such as brute-force attacks, unauthorized access, or privilege misuse.
Key Log Files on Linux Systems
Log File | Description
/var/log/auth.log | Authentication, sudo, SSH login attempts
/var/log/secure | Equivalent to auth.log in RHEL-based distros
/var/log/syslog | General system events, kernel messages
/var/log/messages | Daemon and system messages (RHEL/CentOS)
/var/log/wtmp | Binary log of user logins and reboots
/var/log/btmp | Failed login attempts (binary)
/var/log/lastlog | Last login of all users
/var/log/sudo.log | Optional sudo log file (depends on configuration)
Note: Depending on the Linux distribution, the location and structure of logs may vary. Debian/Ubuntu use auth.log, while RHEL/CentOS typically use secure.
Authentication Logs: SSH and Sudo Activity
Authentication events are among the most critical logs for Blue Team monitoring. They help detect brute-force attacks, credential misuse, and lateral movement.
Example: SSH Failed Login
Jun 30 14:45:21 server sshd[1183]: Failed password for root from 192.168.0.10 port 54022 ssh2
Fields:
* Timestamp: Jun 30 14:45:21
* Process: sshd[1183]
* Message: Failed password
* User: root
* Source IP: 192.168.0.10
* Port: 54022
* Protocol: ssh2
Use case: Detection of brute-force or dictionary attacks from a specific source IP.
Example: SSH Successful Login
Jun 30 14:45:24 server sshd[1183]: Accepted password for root from 192.168.0.10 port 54022 ssh2
A sequence of failed followed by successful logins from the same IP may indicate credential guessing or stolen credentials.
Sudo Usage Detection
Sudo allows users to execute commands as another user (typically root). Monitoring sudo usage is key to detecting privilege escalation or misuse.
Example: Sudo Log Entry (in auth.log):
Jun 30 14:47:11 server sudo:     joao : TTY=pts/0 ; PWD=/home/joao ; USER=root ; COMMAND=/bin/bash
Interpretation:
* User joao executed /bin/bash as root
* Executed from terminal pts/0, current directory /home/joao
Use case: Identify privilege escalation, lateral movement, or shell access as root.
Alternative configuration:
Some systems log sudo activity in a dedicated /var/log/sudo.log if enabled:
Defaults logfile="/var/log/sudo.log"

grep "Failed password" /var/log/auth.log

* Show recent logins (from binary wtmp)

* Show failed logins (from binary btmp)

Event Correlation Techniques
A strong detection capability involves correlating multiple related events. Some useful correlation techniques include:
* Brute-force Detection
* Pattern: High number of Failed password entries within a short time span
* Correlation: Single IP → Multiple usernames or multiple attempts to a single username
* Response: Block IP or initiate account lockout rule
* Credential Stuffing
* Pattern: Same password attempted across many usernames
* Source: Often from automated tools using leaked credentials
* Successful Login After Multiple Failures
* Pattern: Failed password × N → Accepted password
* Example:
Jun 30 20:11:03 sshd[2311]: Failed password for root from 203.0.113.9  Jun 30 20:11:06 sshd[2312]: Failed password for root from 203.0.113.9  Jun 30 20:11:09 sshd[2313]: Accepted password for root from 203.0.113.9
* Use case: Flag as compromised if login succeeded after multiple failures
* Unusual User Activity
* Pattern: Non-privileged user invoking sudo for binaries like netcat, bash, or wget
* Detection via:
grep "sudo" /var/log/auth.log | grep -E 'nc|bash|wget|curl'
Threat Hunting Techniques on Linux Logs
Technique 1: Hunting Interactive Root Access
Look for direct shell sessions as root (especially unexpected ones):
grep 'COMMAND=/bin/bash' /var/log/auth.log | grep 'USER=root'
Technique 2: Looking for Lateral Movement via SSH
Correlate login events from internal IPs that are not part of the jump host or bastion:
grep "Accepted password" /var/log/auth.log | grep -vE '192\.168\.0\.1|10\.0\.0\.1'
Technique 3: Monitoring Sudden Sudo Usage Spike
Generate usage frequency per user:
grep "sudo" /var/log/auth.log | awk '{print $1, $2, $3, $9}' | sort | uniq -c | sort -nr
Useful to flag sudden or unusual use of sudo from accounts that normally don’t escalate.
Technique 4: Detecting User Enumeration Scans
grep "Invalid user" /var/log/auth.log | awk '{print $(NF)}' | sort | uniq -c | sort -nr
Track usernames being probed to identify attempts at discovery before access.
Parsing and Enrichment with Tools
Use of ausearch for auditing (if auditd is enabled)
ausearch -m USER_LOGIN -ts recentausearch -ua 1001
Useful for retrieving user-specific login sessions and mapping UID to usernames.
Log aggregation example with syslog to central server
Configuration in /etc/rsyslog.conf:
*.* @@logserver.local:514

-w /etc/passwd -p wa -k passwd_changes-w /bin/su -p x -k su_usage
Can help track command usage and critical file modifications.

Foundations of Log Analysis for Cyber Defense - 2.2 Windows Event Logs and Security Monitoring
Introduction
Windows Event Logs are one of the pillars of visibility in Microsoft environments. All security-relevant activity, such as authentications, process creation, privilege changes, and remote connections, is natively logged by the operating system. The ability to interpret specific events is critical to detecting attacks such as brute-force, malware use, execution of administrative commands, or persistence through privilege escalation.
Types of Windows Event Logs
Windows classifies its logs into three main categories:
System Logs Information about drivers, hardware failures, and operating system services.
Application Logs Events generated by software installed on the system (e.g., SQL Server, Office, Chrome).
Security Logs Main focus for the Blue Team. Contains authentication, account changes, process creation, use of credentials, among others.
Access via Event Viewer: Start > Run > eventvwr.msc
Key Event IDs for Blue Team Analysts
Event ID | Description | Use Case
4624 | Successful logon | RDP, SMB, interactive or scheduled logons
4625 | Failed logon | Brute-force attempts or invalid credentials
4634 | Logoff event | Session closure
4648 | Logon using explicit credentials | Lateral movement (runas, PSRemoting)
4672 | Special privileges assigned to new logon | Admin or SYSTEM-level access
4688 | New process creation | Malware, tools like PowerShell or cmd
4689 | Process termination | Hiding evidence, persistence cleanup
4697 | New service installed | Persistence via service creation
4720 | User account created | Rogue user creation
4723 | Password change attempt | Account manipulation
4769 | Kerberos ticket requested (TGS) | Pass-the-Ticket detection
Example: Successful Logon (4624)
Log Name: Security  Event ID: 4624  Logon Type: 10 (RemoteInteractive)  Account Name: administrator  Source Network Address: 192.168.1.100
Interpretation:
Administrator successfully authenticated via RDP from 192.168.1.100.
Logon Types (commonly used for detection logic):
* 2 = Interactive (local)
* 3 = Network (SMB, CIFS)
* 5 = Service
* 10 = Remote Desktop
* 11 = Cached Interactive

Event ID: 4625  Failure Reason: Unknown user name or bad password  Logon Type: 3  Account Name: admin  Source Network Address: 10.10.10.5
Interpretation:
Failed network logon attempt, likely via SMB or shared folder access.
Use case:
Detection of brute-force or lateral movement attempts.
Example: Process Creation (4688)
Event ID: 4688  New Process Name: C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe  Command Line: powershell.exe -EncodedCommand SQBtAGUAbABvAGcA
Use case:
Flag command line usage of PowerShell with Base64-encoded content. Common in malware execution and evasive scripts.

Common Detection Use Cases
Use Case 1: RDP Brute-Force
* Many 4625 events followed by a 4624 with Logon Type 10
* Correlation:
* Source IP remains the same
* Usernames attempted vary
* Time window is narrow (e.g., <5 minutes)
Use Case 2: Execution of Suspicious Tools
* 4688 for cmd.exe, powershell.exe, mshta.exe, rundll32.exe

* Example: attacker uses runas or invokes Invoke-Command over WinRM
Use Case 4: Persistence via Service Installation
* 4697 followed by 4624 or 4688 indicating execution
* Services with unusual names or paths (e.g., in temp directories)

* EventID

Best Practices
* Enable advanced audit policy (Audit Process Creation, Audit Logon Events, etc.)
* Configure Group Policy to include command-line logging:
* Administrative Templates > System > Audit Process Creation > Include command line in process creation events
* Retain at least 90–180 days of Security.evtx logs
* Use Sysmon alongside native logs for deeper telemetry (e.g., file writes, registry access)
Technique 1: Detecting Credential Access and Privilege Escalation
Correlate Event ID 4648 (explicit credentials) with 4624 (logon) and 4672 (admin privileges)
Use case: Adversaries executing tools like runas, PsExec, or Invoke-Command over WinRM often generate these events.
Example Sequence:
Event ID 4648: A logon was attempted using explicit credentialsEvent ID 4624: Successful logon (Logon Type 3 or 10)Event ID 4672: Special privileges assigned (e.g., SeDebugPrivilege)
Detection Logic:
* Track rare use of Event ID 4648
* Cross-reference account name and source IP
* Confirm if the account used received elevated privileges (4672)
Technique 2: Hunting for Malicious PowerShell Execution
Indicators in 4688 (process creation)
* Use of powershell.exe or pwsh.exe
* -EncodedCommand
* -WindowStyle hidden, -nop, -exec bypass
* Download commands: Invoke-WebRequest, System.Net.WebClient
Example from Event Viewer:
New Process Name: C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe  Command Line: powershell.exe -nop -w hidden -EncodedCommand SQBtAGUAbABvAGcA
Hunting Tip:
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4688} | Where-Object { $_.Message -match "powershell.*EncodedCommand" } |Format-Table TimeCreated, Message -AutoSize
Map to MITRE ATT&CK T1059.001 (Command and Scripting Interpreter: PowerShell)
Technique 3: Detecting Process Injection and Evasion
Indicators:
* Suspicious use of rundll32.exe, regsvr32.exe, mshta.exe
* Unusual parent processes like explorer.exe spawning cmd.exe or powershell.exe
* Direct execution from AppData, Temp, or mounted ISO paths
Example:
4688: New Process Name: C:\Users\user\AppData\Local\Temp\evil.exeParent Process Name: C:\Windows\explorer.exe
Detection:
* Highlight non-signed binaries executed from user-writable paths
* Watch for mismatch in parent/child process behavior
Technique 4: Account Manipulation and Persistence
Monitor Event IDs:
* 4720: User account created
* 4722: Account enabled
* 4732: User added to local admin group
* 4798: User's group membership enumeration (often by attackers before privilege escalation)
Example:
A user account was created.Subject: SYSTEMNew Account Name: supportPrivileges: Administrator
Detection Logic:
* Any non-authorized user creating accounts
* SYSTEM creating accounts during odd hours
* Multiple group changes in a short time span

While native Event Logs are useful, Sysmon provides higher-fidelity telemetry with richer context. It is often used in conjunction with Windows Event Logs in advanced Blue Team setups.

Foundations of Log Analysis for Cyber Defense - 2.3 Comparison Between Linux and Windows Logging
Introduction
Windows and Linux are both widely used operating systems in enterprise environments, and each has its own architecture for generating, storing, and querying logs. For security analysts, understanding these differences is critical to creating a cohesive approach to monitoring, threat detection, and incident response.
This topic compares the two operating systems in terms of log sources, format, granularity, access, and practical use in the context of cybersecurity.
Structural and Format Differences
Aspect | Linux | Windows
Log Format | Plain text (syslog), CSV, JSON | Binary (EVTX), XML (in some tools)
Storage Location | /var/log/ | %SystemRoot%\System32\winevt\Logs\
Access Method | CLI tools (grep, journalctl) | GUI (Event Viewer), PowerShell
Log Rotation | Managed by logrotate | Automatic overwrite or manual archive
Timestamps | Human-readable / UTC | UTC with local time context
Custom Audit Tools | auditd, Syslog-NG, rsyslog | Advanced Audit Policy, Sysmon
Authentication Logging Comparison
Scenario | Linux Example Log | Windows Equivalent (Event ID)
Successful login (local/SSH) | Accepted password for user from IP | 4624 (Logon Success)
Failed login | Failed password for invalid user from IP | 4625 (Logon Failure)
Privilege escalation | sudo: user : COMMAND=/bin/bash | 4672 (Admin privileges assigned), 4688 (command run)
Remote access (RDP or SSH) | sshd: session opened for user from IP | 4624 (Logon Type 10 – RDP)
Logoff | session closed for user | 4634 (Logoff)
Observation:
While Linux logs typically use simple, readable lines, Windows logs offer richer metadata but require tools for decoding binary .evtx format.
Process Execution Comparison
Event | Linux (auth.log or auditd) | Windows (Event Viewer or Sysmon)
Process creation | auditd: execve("/bin/bash", ...) | 4688: New Process Created
Command parameters | auditd or shell history (.bash_history) | 4688 + command line (if enabled via policy)
File execution tracking | Not default; auditd or inotify required | Sysmon Event ID 1 (Process Create)
Parent process identification | Manual via ps -ef --forest or audit logs | Available in 4688 and Sysmon
File Access and Modification Logging
Action | Linux | Windows
File read/write/open/delete | Requires auditd or fanotify | Sysmon (Event IDs 11, 23)
Log location | /var/log/audit/audit.log | Sysmon or third-party EDR
Registry change logging | Not applicable | Sysmon Event ID 13 (Registry Set Value)
Insight:
Linux requires explicit configuration (auditd, incron, audit rules) to generate logs that are similar in granularity to what Windows provides nativamente via Sysmon or Group Policy Audit Policies.
Log Visibility and Coverage
Area | Linux Coverage | Windows Coverage
Authentication events | Strong via auth.log, btmp | Strong via Security Log
Process activity | Weak by default; strong with auditd | Moderate by default; strong with Sysmon
Network activity | Weak; requires IPTables, Suricata | Weak; requires Sysmon or ETW-based tools
File system access | Requires auditd or fanotify | Supported via Sysmon
Script execution detection | Manual or auditd | Via 4688 and PowerShell logging
Query and Search Capabilities
Capability | Linux | Windows
Basic log query | grep, awk, journalctl | Event Viewer GUI, Get-WinEvent
Structured search | JSON logs with jq, ELK integrations | PowerShell with filters, Splunk/Elastic
Log forwarding | rsyslog, syslog-ng, auditd | Windows Event Forwarding, GPO
SIEM integration | Fluentd, Beats, syslog formats | Windows agents (Winlogbeat, NXLog, etc.)
Response to Attacker Behavior (Example Mapping)
Case Study:
Attacker logs in remotely and executes a script to escalate privileges.
Step | Linux | Windows
Initial access | SSH accepted log in auth.log | Event ID 4624 (Logon Type 10)
Enumeration | whoami, id (may not be logged) | Command line in 4688 or Sysmon
Privilege escalation | sudo or SUID binary usage | Event ID 4672 + process with admin token

Analyst Takeaways
* Linux logs are easier to read but require more effort to generate granular telemetry
* Windows logs are richer but harder to parse manually without GUI or automation
* Both systems benefit greatly from centralized collection, parsing, and correlation
* Enabling verbose logging (PowerShell transcript, Sysmon, auditd) is critical in both environments
* Use normalization layers in SIEMs to unify event fields from both platforms (e.g., source_ip, user_name, process_name)
Foundations of Log Analysis for Cyber Defense - 3.1 Firewall Logs and Perimeter Monitoring
Introduction
Firewalls represent the first line of defense in network security. They control traffic flow based on predefined rules and are responsible for blocking unauthorized access attempts. Firewall logs are essential for visibility into network activity and are often the first source of evidence during an intrusion attempt.
Analyzing firewall logs allows Blue Team professionals to:
* Detect port scans and reconnaissance activity
* Identify unauthorized access attempts
* Observe inbound and outbound traffic patterns
* Correlate alerts with other data sources such as IDS, endpoint logs, or proxy logs
Common Firewall Types and Log Formats
Firewall Type | Examples | Log Format
Hardware Firewall | Cisco ASA, FortiGate | Syslog, proprietary
Host-Based Firewall | iptables, UFW, Windows FW | Plaintext, CSV, EVTX
Cloud Firewall | AWS SG/NACLs, Azure NSG | JSON, CloudWatch, Log Analytics
Web Application Firewall | ModSecurity, AWS WAF | JSON, audit log text
Most enterprise firewalls support Syslog output, which makes log ingestion into SIEM platforms straightforward.
Anatomy of a Firewall Log Entry
Example: iptables log (Linux, via syslog)
Jan  1 14:45:31 server kernel: [UFW BLOCK] IN=eth0 OUT= MAC=00:15:5d:01:02:03 SRC=192.168.0.10 DST=10.0.0.5 LEN=60 TOS=0x00 PREC=0x00 TTL=64 ID=54321 PROTO=TCP SPT=51515 DPT=22 WINDOW=29200 RES=0x00 SYN URGP=0
Parsed Fields:
* Action: BLOCK
* Source IP: SRC=192.168.0.10
* Destination IP: DST=10.0.0.5
* Protocol: PROTO=TCP
* Source Port: SPT=51515
* Destination Port: DPT=22
* Flags: SYN (connection attempt)
Use Case: SSH access attempt blocked by firewall.
Example: Cisco ASA Log Entry
%ASA-6-106015: Deny TCP (no connection) from 192.168.1.100/45678 to 10.0.0.10/80 flags RST on interface outside
* Severity: 6 (Informational)
* Denied TCP traffic (no stateful connection established)
* TCP flag RST indicates a reset
* Traffic was blocked on the "outside" interface
Common Blue Team Use Cases
Port Scanning Detection
* High volume of denied connections to multiple ports
* Typically fast and sequential (e.g., ports 20–1024)
grep "DPT=" /var/log/syslog | awk '{print $NF}' | sort | uniq -c | sort -nr
Unusual Inbound Traffic
* Logs showing source IPs from the internet targeting internal systems
* Attempt to access uncommon services (e.g., telnet, NetBIOS, SNMP)
Internal Lateral Movement
* Unexpected east-west traffic between hosts
* May indicate malware propagation, credential reuse, or internal recon
Blocked Outbound Traffic
* Systems attempting to reach known malicious IPs or non-standard ports
* Example: malware beaconing attempts on port 8080 or 53 (DNS)
Logging Best Practices
* Log both allowed and denied traffic, especially denied connections
* Always timestamp logs in UTC for cross-source correlation
* Clearly label interfaces and zones (e.g., inside, outside, DMZ)
* Normalize log fields for SIEM ingestion
* Forward logs to a centralized collector via UDP/TCP Syslog
Syslog forwarding example (Linux):
:msg, contains, "UFW" @192.168.1.10:514
SIEM Queries and Detection Rules
Splunk Example: Blocked port scan detection
index=firewall action=blocked | stats count by src_ip, dest_port | where count > 10
Elastic Search (KQL)
action: "BLOCKED" and destination.port >= 0
Microsoft Sentinel (KQL)
CommonSecurityLog| where DeviceVendor == "Fortinet"| where Message has "Deny"| summarize TotalAttempts = count() by SourceIP, DestinationPort| where TotalAttempts > 20
Event Enrichment and Context
To enhance analysis, enrich firewall logs with:
* GeoIP: Identify source country for anomalies (e.g., login from foreign region)
* Threat Intel Feeds: Match IPs against blocklists (e.g., AbuseIPDB, AlienVault OTX)
* Traffic direction tags: inbound, outbound, lateral
* Service tags: Based on destination port (e.g., DPT=3389 = RDP)
This allows more meaningful alerting and contextual triage.
Summary
Firewall logs provide foundational visibility into inbound, outbound, and lateral traffic within an organization. When enriched, centralized, and correlated with endpoint or authentication logs, they become critical for early threat detection and forensic response. Properly tuned firewall logging policies and consistent parsing across systems allow analysts to detect reconnaissance, unauthorized access attempts, and malware behavior in near real time.
Foundations of Log Analysis for Cyber Defense - 3.2 IDS/IPS Logs (Snort, Suricata)
Introduction
Intrusion Detection Systems (IDS) and Intrusion Prevention Systems (IPS) are key components in a layered defense strategy. While firewalls focus on traffic control, IDS/IPS solutions analyze traffic contents and patterns for known and unknown threats.
IDS: Detects and alerts on suspicious activity but does not block.
IPS: Actively blocks or drops malicious traffic based on detection logic.
Popular open-source IDS/IPS tools:
* Snort (Cisco): Signature-based detection
* Suricata (OISF): Multi-threaded engine with IDS/IPS/NSM capabilities
* Zeek (formerly Bro): Network security monitoring, not signature-focused
Understanding IDS/IPS Logs
Logs from IDS/IPS systems usually include:
* Timestamp: When the event occurred
* Signature ID: Rule that triggered the alert
* Source/Destination IP and Ports
* Protocol and packet details
* Message/Classification: Short description of the threat
* Severity/Priority
Example: Snort Alert Log
[**] [1:1000001:1] ET SCAN Nmap Scripting Engine User-Agent Detected [**][Classification: Attempted Information Leak] [Priority: 2]06/30-14:22:10.123456 192.168.1.100:58000 -> 10.0.0.20:80TCP TTL:64 TOS:0x0 ID:1111 IpLen:20 DgmLen:48***A**** Seq: 0x0  Ack: 0x0  Win: 0x400  TcpLen: 20
Explanation:
* SID: 1000001 – custom or Emerging Threats rule
* Classification: Info leak attempt
* Traffic: From internal system to web server on port 80
* User-Agent detection: Possibly an Nmap scan with NSE scripts
Example: Suricata EVE JSON Log (for ingestion in SIEM)
{  "timestamp": "2025-06-30T14:22:10.123456Z",  "event_type": "alert",  "src_ip": "192.168.1.100",  "src_port": 58000,  "dest_ip": "10.0.0.20",  "dest_port": 80,  "proto": "TCP",  "alert": {    "action": "allowed",    "gid": 1,    "signature_id": 2100498,    "rev": 3,    "signature": "ET SCAN Nmap Scripting Engine User-Agent Detected",    "category": "Attempted Information Leak",    "severity": 2  }}
Benefits of Suricata JSON:
* Easy ingestion into SIEM tools
* Structured format for correlation
* Enables dashboards and alerting with high precision
Use Cases for Blue Team
1. Reconnaissance Detection
* Rule triggered by unusual User-Agent, malformed DNS, or SMB probes
* Suricata/Snort rule examples:
* Nmap detection
* Masscan signatures

2. Exploit Attempts

Correlation Techniques
* Enrich with Threat Intelligence: Match IPs/domains against threat feeds
* Correlate by UID: Suricata can assign flow UIDs to track sessions
* Pivot on Signature ID: Link alerts to MITRE ATT&CK techniques

Feature | IDS | IPS
Action | Detects and alerts only | Detects and blocks traffic
Risk | Lower (no disruption) | Higher (possible false positives)
Deployment | Passive (SPAN port, TAP) | Inline (in path of traffic)
Use case | Visibility and detection | Real-time enforcement
Tuning and False Positive Reduction
* Suppress noisy rules irrelevant to the environment
* Customize signatures based on internal threat model
* Use threshold rules to avoid alert floods
* Monitor alert-to-action ratio for IPS (avoid blocking legitimate traffic)

suppress gen_id 1, sig_id 2010935, track by_src, ip 192.168.1.50
Foundations of Log Analysis for Cyber Defense - 3.3 DNS Log Analysis
Introduction
DNS (Domain Name System) is one of the most critical services in a network. Nearly all network communication starts with a DNS request, making DNS logs a goldmine for detection and threat hunting.
DNS logs provide visibility into:
* Domain lookups by internal hosts
* Indicators of malware or C2 communication
* DNS tunneling and data exfiltration
* Typo-squatting and phishing domain access
Analyzing DNS traffic can reveal threats that evade traditional firewalls or antivirus tools.
Common Sources of DNS Logs
Source | Example | Format
DNS Resolver Logs | BIND, Unbound, Windows DNS | Text, JSON
Passive DNS Sensors | Zeek, SecurityOnion, Suricata | JSON, TSV
Cloud Logs | AWS Route 53, GCP Cloud DNS | JSON

* Log both queries and responses (for context)

* Store logs in a SIEM with enrichment
* Apply threat intelligence feeds to DNS queries

* T1046 – Network Service Scanning
* T1095 – Non-Application Layer Protocol (custom DNS C2)

DNS logs are a powerful source of detection and intelligence. A mature Blue Team operation should have full visibility into DNS activity and actively monitor for suspicious domains, traffic patterns, and signs of abuse.

Foundations of Log Analysis for Cyber Defense - 4.1 Fundamentals of Log Correlation in Threat Hunting
Introduction
Log correlation is the process of linking events from multiple sources, across time and systems, to form a cohesive view of what occurred within an environment. In threat hunting, correlation is what transforms isolated data points into actionable insights. It allows Blue Team professionals to identify complex attacks, detect lateral movement, and reconstruct adversary behaviors that evade traditional detection mechanisms.
Whereas SIEM alerts are often based on static rules, manual and hypothesis-driven correlation is dynamic, contextual, and based on understanding attacker tactics, techniques, and procedures (TTPs).
Why Correlation Matters in Hunting
An attacker rarely uses a single action. Consider a compromise involving:
* Phishing click in a proxy log
* Malicious payload written to disk (EDR log)
* New scheduled task created (Windows event)
* Outbound C2 beacon to an IP (Firewall log)
* Lateral movement via RDP (Authentication logs)
Individually, none of these may trigger an alert. But when correlated, they form a clear narrative of compromise.
Types of Log Correlation
1. Temporal Correlation
* Events that occur within a specific timeframe
Example: A suspicious PowerShell script within 5 minutes after a new service is created.
2. Identity Correlation
* Events linked by user, host, or session
Example: User jsmith logs in via VPN, then accesses five critical servers using RDP.
3. Network Correlation
* Based on IP addresses, DNS names, and ports
Example: Beaconing to an IP that was also queried in DNS logs and later seen in firewall logs.
4. Process/Parent-Child Correlation
* Especially in EDRs, linking parent and child processes
Example: winword.exe spawning powershell.exe followed by network activity.
5. Threat Intelligence Correlation
* Matching known IOCs against observed logs
Example: Outbound connections to a domain listed in a threat intel feed.
Practical Examples
Example 1: Credential Dumping and Lateral Movement
* Logon events show successful access to DC1 from HR-PC.
* Windows event log shows use of rundll32 shortly after login.
* EDR detects a memory dump of lsass.exe.
* Two minutes later, the same user logs in to FINANCE-SVR.
Correlation: All these events occurred within a 6-minute window, linked by the same user, indicating possible credential theft and lateral movement.
Example 2: Beaconing to C2
* DNS logs show repeated queries to xyz-cdn.com.
* Proxy logs show regular GET requests every 60 seconds to the same domain.
* Firewall logs show outbound connections to IP 192.0.2.50:443.
Correlation: Repeated behavior indicates C2 beaconing using DNS and HTTP over TLS, possibly with domain fronting.
Tools and Techniques
Tool | Use Case
SIEM (Splunk, Elastic, Sentinel) | Correlation rules and searches
Threat Hunting Platforms (Velociraptor, LimaCharlie, Gravwell) | Timeline reconstruction
Jupyter Notebooks | Custom correlation via pandas, timelines
EDR XDR Consoles | Process relationships, lateral movement
Hunting Methodology Example
Hypothesis: Adversary has persistence on an endpoint and is exfiltrating data via PowerShell.
Log Sources to Correlate:
* EDR logs (PowerShell usage, parent process relationships)
* Authentication logs (initial access, session tracking)
* Proxy logs (unusual domain access)
* File creation logs (temp files, encoded payloads)
Steps:
* Find unusual PowerShell usage (e.g. Base64 encoded commands)
* Trace parent process (was it Word, Outlook, WMI?)
* Check if the same user accessed sensitive systems afterward
* Look for data transfer in proxy/firewall logs to rare destinations
Challenges and Solutions
Challenge: Timestamps differ across logs
Solution: Normalize time via UTC, ensure NTP is enforced on all endpoints
Challenge: Incomplete data due to log retention gaps
Solution: Extend retention for high-value logs and use full-packet capture for enrichment
Challenge: Volume of data is overwhelming
Solution: Use hunting queries with filters, aggregations, and visualizations (e.g., frequency maps, time series)
Real-World Application
In many red team engagements, lateral movement and data exfiltration go undetected because no single event looks suspicious. However, correlating authentication logs with EDR process trees and DNS/proxy traffic reveals the complete attack chain. Mature Blue Teams rely on this technique to:
* Reconstruct incidents
* Confirm alerts or dismiss false positives
* Discover threats that went unnoticed by automated tools
Foundations of Log Analysis for Cyber Defense - 4.2 Pivoting Across Log Sources (DNS, Proxy, EDR, Authentication)
Introduction
In threat hunting, pivoting means taking one data point (e.g., an IP address, domain, hash, or username) and following its trail across multiple log sources to uncover related events or build a timeline. This is a critical skill when investigating multi-stage attacks, lateral movement, or command and control (C2) activity.
The ability to pivot effectively depends on:
* Knowing where to look (log source awareness)
* Understanding relationships between log types
* Thinking like an attacker and mapping their steps across systems
Key Log Sources for Pivoting
Source | Typical Pivot Elements
DNS logs | Queried domains, client IPs
Proxy logs | URLs, domains, methods, user agents
EDR logs | File hashes, parent-child process chains
Authentication logs | Usernames, logon types, source IPs
Firewall logs | Source/destination IPs, ports
Cloud IAM logs | Actor, action, resource accessed
Example 1: Suspicious Domain in DNS Logs
Initial Indicator:
DNS query for cdn-assets-update[.]com from IP 10.10.5.12
Pivot:
* Proxy logs: Look for 10.10.5.12 contacting the domain — confirm GET/POST behavior, User-Agent anomalies.
* Firewall logs: Check if traffic to resolved IP (e.g., 104.21.11.20) passed outbound.
* EDR logs: What process initiated the DNS query? Often it’s powershell.exe or cmd.exe.
* Authentication logs: Who was logged into the system 10.10.5.12 at the time?
This chain allows you to build attribution, intent, and impact.
Example 2: Suspicious PowerShell Execution
Initial Indicator:
powershell.exe -enc seen in EDR logs from host WIN-07
Pivot:
* Process tree: Was the parent winword.exe? Likely phishing.
* Authentication logs: Which user executed it? Did this user log in elsewhere later?
* DNS/Proxy logs: Any outbound connections following execution?
* EDR telemetry: Were any files dropped or new scheduled tasks created?
Hunting Workflow Diagram
[Indicator: Suspicious IP]                      |           → Firewall logs (verify comms)                      ↓            Proxy logs (URL/path/User-Agent)                      ↓            DNS logs (who resolved domain)                      ↓     EDR logs (which process made the call)                      ↓   Authentication logs (who was logged in)
This recursive pivoting is the foundation of real threat hunting investigations.
Practical Techniques for Pivoting
1. IP-Based Pivot
* Start with an IP from firewall/proxy logs
* Find all user agents and target hosts
* Go backwards: find DNS resolutions for domain/IP
2. Hash-Based Pivot (EDR-centric)
* Start with file hash (e.g., SHA256 from malicious DLL)
* Check all endpoints where it appeared
* Pivot to processes that launched it
3. Username-Based Pivot
* Trace a user across VPN, RDP, internal access
* Find privilege escalation or lateral movement
4. Domain-Based Pivot
* Resolve domain to IPs (DNS logs)
* Search proxy logs for POSTs or payload exfiltration
* Match URL patterns to known malware families (e.g., /upload.php, /gate.php)
5. Beacon Behavior Pivot
* Identify regular timed outbound requests in proxy
* Cross-reference source with EDR to find process origin
* Correlate with DNS domain history
Tools and Queries
Elastic KQL
dns.question.name : "cdn-assets-update.com" | join kind=inner (  process.name : "powershell.exe" AND host.name : "WIN-07")on host.ip
Splunk SPL
index=proxy OR index=firewall| search src_ip="10.10.5.12" OR dest_ip="104.21.11.20"| stats values(uri) by src_ip, user, timestamp
Sigma Rule Example
title: Powershell Invoked After DNS Resolution of Suspicious Domaindetection:  dns:    query: "*cdn-assets-update.com"  edr:    process_name: "powershell.exe"  condition: dns and edr within 5m
Common Pitfalls
Mistake | Risk
Pivoting without timestamp context | May correlate unrelated events
Ignoring NAT or proxy masking | Leads to false attribution of source IPs
Not using session identifiers | Breaks chain of events in multi-user systems
Overlooking failed authentications | Misses credential stuffing or probing attempts
Threat Hunting Example: Lateral Movement Pivot
* Start with an RDP logon (Windows Event ID 4624, Logon Type 10)
* Pivot to EDR logs to check what was executed post-login
* Cross-check with DNS logs to see if outbound domains were contacted
* Look at authentication logs for the same user logging in to other systems
* Add GeoIP/contextual enrichment: did this account ever log in from an unusual location?
Foundations of Log Analysis for Cyber Defense - 4.3 Building Hypothesis-Driven Hunting Playbooks
Introduction
Unlike reactive alert triage, threat hunting is proactive and intelligence-driven. It requires formulating hypotheses about potential attacker behavior and validating (or refutando) those hypotheses through log analysis and correlation.
A hunting playbook is a documented and repeatable process that:
* Starts from a well-structured hypothesis
* Defines scope and required log sources
* Lays out step-by-step procedures
* Uses specific queries and correlation logic
* Ends with documentation and feedback for detection engineering
This approach helps Blue Teams avoid random log searches and instead focus on uncovering adversary behavior patterns that often bypass signature-based detections.
What Is a Threat Hunting Hypothesis?
A hypothesis is a statement that assumes a specific attacker behavior or technique might have occurred within your environment.
Example Hypotheses:
* “An adversary has established persistence using scheduled tasks.”
* “There is beaconing behavior occurring over HTTP every 60 seconds.”
* “An internal user is accessing sensitive data they normally do not touch.”
Good hypotheses are specific, testable, and adversary-aligned.
Sources of Hypotheses
Source | Example
MITRE ATT&CK | T1053.005 – Scheduled Task/Job: Scheduled Task
Threat Intelligence | APT29 using custom DNS tunneling
Detection gaps | No alerts exist for use of LOLBins (e.g. mshta.exe)
Baseline deviation | Spike in authentication from service accounts
Purple teaming results | Uncovered behavior not yet covered by rules
Building the Playbook Step by Step
1. Define the Hypothesis
Adversaries may have achieved persistence using schtasks.exe on endpoints with recent VPN logins.
2. Set Objectives
* Identify machines where scheduled tasks were created manually
* Link actions to user activity
* Detect execution of those tasks
* Identify any payloads or outbound connections tied to them
3. Identify Log Sources
Source | Required Data
Windows Event Logs | Task creation (Event ID 4698), process execution
EDR Logs | Parent-child process chain (schtasks.exe)
VPN Logs | Remote access timestamps and users
Proxy/DNS Logs | Any post-task execution outbound traffic
4. Create Search Queries
Splunk
index=windows EventCode=4698 CommandLine="*schtasks*" | stats count by host, user, CommandLine, _time
Elastic KQL

Foundations of Log Analysis for Cyber Defense - 4.4 Hunting for Lateral Movement and Persistence
Introduction
Lateral movement and persistence are key post-exploitation phases in adversary operations. After initial access, attackers aim to move within the network to access valuable assets and establish mechanisms to maintain control, even after reboots or account changes.
Detecting these actions before impact requires correlating logs from different layers — endpoint, authentication, network, and execution — and understanding what legitimate behavior looks like in order to spot deviations.
Common Techniques for Lateral Movement
Technique | MITRE ATT&CK ID | Description
Remote Desktop Protocol | T1021.001 | RDP access between internal hosts
Pass-the-Hash / Ticket | T1550.002 / .003 | Reuse of stolen credentials or Kerberos tickets
Windows Admin Shares | T1021.002 | Using SMB (C$, ADMIN$) to execute remotely
PsExec | T1569.002 | Executing commands on remote systems via service
WMI/WMIC | T1047 | Remote code execution via Windows Management
PowerShell Remoting | T1021.006 | Remote sessions using WinRM
Common Techniques for Persistence
Technique | MITRE ATT&CK ID | Description
Scheduled Task / Cron Job | T1053 | Creates tasks that re-execute payloads
Registry Run Keys | T1547.001 | Modifies keys to auto-start payloads
Service Binary Modification | T1543.003 | Changes legitimate service paths
Startup Folder Injection | T1547.001 | Drops payloads into startup folders
WMI Event Subscriptions | T1546.003 | Uses WMI to execute code on specific triggers
Hunting Methodology
Step 1: Define Known Patterns
Create a list of behaviors associated with lateral movement and persistence (e.g., execution of wmic.exe, creation of scheduled tasks, use of remote shares).
Step 2: Identify Key Logs
Source | What to Look For
Windows Event Logs | Logon events (4624/4625), service creation (7045), tasks
Sysmon | Process creations, parent-child anomalies, remote threads
EDR Logs | Lateral tools, signed binaries used for abuse (LOLBins)
Firewall | Inbound SMB/RDP traffic, new connections between hosts
DNS / Proxy | Beaconing from new internal IPs
Step 3: Correlate Behavior
* Look for logon events followed by unusual remote execution
* Detect abnormal parent-child relationships (e.g., explorer.exe spawning wmic.exe)
* Correlate timestamps and user sessions across systems
Example 1: Suspicious RDP Followed by Task Creation
* Event ID 4624 (Logon Type 10) from host HR-WS01 using user svc_hr
* 2 minutes later: Event ID 4698 (Scheduled Task Created) on FINANCE-SRV01
* EDR confirms task runs cmd.exe /c powershell -enc ...
* Proxy logs show outbound C2 connection from FINANCE-SRV01 to unknown IP
This sequence suggests lateral movement into FINANCE-SRV01 with persistence setup and external communication.
Example 2: WMIC Lateral Movement
* EDR logs show:
Parent: svchost.exe → Child: wmic.exe /node:10.0.4.15 process call create ...
* Sysmon reveals remote process creation on 10.0.4.15
* Authentication logs show svc_ops account used outside of its normal asset group
* Follow-up shows scheduled task created on remote machine
This could indicate automated lateral spread via WMIC and scheduled tasks.
Sigma Rule Example: Suspicious Use of WMIC
title: WMIC Remote Executionlogsource:  category: process_creationdetection:  selection:    Image: 'C:\\Windows\\System32\\wbem\\WMIC.exe'    CommandLine|contains: ' /node:'  condition: selectionfields:  - Image  - CommandLine  - ParentImage
Hunting Queries
Elastic KQL – Logon Followed by Task Creation
event.code : "4624" AND logon_type : "10"| join type=inner [  event.code : "4698"] on host.name, user.name
Splunk – Parent-Child Process Abnormalities
index=edr OR index=sysmon| transaction host startswith=(process_name="explorer.exe") endswith=(process_name="wmic.exe")| stats count by host, user, parent_process, child_process
Pro Tips
* Focus on cross-host behavior: Lateral movement by nature spans systems
* Watch for anomalous parent-child process combos (e.g., winword.exe spawning powershell.exe)
* Use time-bounded correlation to reduce noise and enhance accuracy
* Combine with baseline deviation: Look for persistence on systems not typically associated with changes
Practical Hunting Playbook (Example)
Playbook Title: Detecting Lateral Movement via PsExec
* Hypothesis: "An attacker is using PsExec to spread laterally."
* Required Logs: Sysmon, EDR, Windows Event Logs, Firewall
* Hunting Steps:
* Search for psexec.exe, psexecsvc.exe, or service creation via Event ID 7045

Foundations of Log Analysis for Cyber Defense - 4.5 Using Sigma, KQL, SPL, and Custom Queries for Detection Engineering
Introduction
Detection engineering is a discipline that combines threat intelligence, log analysis, and syntax-based rule creation to proactively identify adversary behaviors in an environment. It bridges the gap between threat hunting and automated detection.
To build high-quality detections, Blue Team professionals must be fluent in query languages and formats like:
* Sigma – a YAML-based generic detection rule format, easily converted into platform-specific rules (Elastic, Splunk, Sentinel, etc.)
* KQL (Kusto Query Language) – used in Microsoft Sentinel and Defender
* SPL (Search Processing Language) – used in Splunk
* Custom SQL-like syntax – used in platforms like QRadar, Graylog, and others
Part 1: Sigma Rules
Sigma provides a way to write detection logic once and convert it into multiple backend formats using tools like sigmac.
Structure of a Sigma Rule:
title: Suspicious PowerShell Executionid: abc123description: Detects encoded PowerShell payloads often used in phishing or malwarestatus: experimentallogsource:  product: windows  category: process_creationdetection:  selection:    Image|endswith: '\powershell.exe'    CommandLine|contains:      - ' -enc '      - ' -EncodedCommand '  condition: selectionlevel: high
Usage:
sigmac -t splunk suspicious_powershell.yml
This outputs a ready-to-use SPL query for Splunk.
Part 2: KQL (Microsoft Sentinel / Defender)
KQL is designed to query time-series data. It's commonly used in Sentinel, Microsoft Defender for Endpoint, and Log Analytics.
Example – Detect PowerShell with base64 payload:
DeviceProcessEvents| where FileName =~ "powershell.exe"| where ProcessCommandLine has " -enc " or ProcessCommandLine has " -EncodedCommand"| project Timestamp, DeviceName, InitiatingProcessAccountName, ProcessCommandLine
Another example – Lateral movement via RDP:
SigninLogs| where NetworkLocationDetails has "Remote Desktop"| where Location != "Expected Country"
Part 3: SPL (Splunk Search Processing Language)
SPL is used for powerful, time-bound and field-based searches in Splunk.
Example – Search for scheduled task creation and follow-up execution:
index=wineventlog EventCode=4698 OR EventCode=4688| eval event_type=case(EventCode==4698,"TaskCreated",EventCode==4688,"ProcessExec")| transaction host startswith=(event_type="TaskCreated") endswith=(event_type="ProcessExec") maxspan=15m| table _time, host, user, CommandLine, parent_process_name, event_type
Example – Search for unusual parent-child process chains:
index=edr OR index=sysmon| where parent_process_name="winword.exe" AND process_name="powershell.exe"| stats count by host, CommandLine, _time
Part 4: Combining Languages with Threat Frameworks
You can build detection rules based on MITRE ATT&CK TTPs and map them to logs using each of the above languages.
T1059 – Command and Scripting Interpreter:
* Sigma: process_creation with suspicious scripting languages
* KQL: DeviceProcessEvents with PowerShell and encoded commands
* SPL: index=sysmon with scripting tool command lines
This allows for multi-platform parity of your detection logic.
Example Exercise: Detecting PsExec Use
Sigma Rule Example:
title: PsExec Remote Executionlogsource:  category: process_creationdetection:  selection:    Image|endswith:      - 'psexec.exe'      - 'psexecsvc.exe'  condition: selectionlevel: high
Converted to KQL:
DeviceProcessEvents| where FileName in~ ("psexec.exe", "psexecsvc.exe")| project DeviceName, Timestamp, InitiatingProcessAccountName, FolderPath
Converted to SPL:
index=edr OR index=sysmonprocess_name="psexec.exe" OR process_name="psexecsvc.exe"| stats count by host, user, parent_process, CommandLine
Tips for Effective Detection Engineering
* Always test queries in a lab or threat simulation environment (e.g., with Atomic Red Team)
* Start from hypotheses or threat intel, not just generic alerts
* Tag each rule with MITRE ATT&CK technique IDs and log source types
* Use fields like parent-child process relationships, network behavior, frequency anomalies
* Prioritize low-noise, high-fidelity rules and fine-tune over time
* Use dedicated Git repos to version-control Sigma rules
Summary
By mastering Sigma, KQL, SPL and similar query languages, a Blue Team analyst can:
* Build portable detection rules
* Correlate multi-source logs
* Write rules aligned with threat actor TTPs
* Reduce alert fatigue by making rules context-aware
* Accelerate incident response with precision
Foundations of Log Analysis for Cyber Defense - 4.6 Integrating Threat Intelligence into Correlation
Introduction
Threat Intelligence (TI) is critical in enhancing log analysis and threat hunting. While logs tell what happened, threat intelligence provides context on why it matters, helping analysts prioritize, correlate, and act faster.
Integrating TI feeds allows you to enrich logs with known indicators of compromise (IOCs) such as IP addresses, domains, URLs, file hashes, and TTPs. When properly used, TI can amplify detections, guide hypothesis-driven hunts, and reduce dwell time.
Types of Threat Intelligence
Type | Description
Tactical (IOCs) | IPs, hashes, domains, user agents used in recent attacks
Operational | Details about specific campaigns, malware families, TTPs
Strategic | High-level trends about threat actors and their goals
Technical | Indicators extracted from malware samples or network traffic
For log correlation, Tactical and Operational TI are the most actionable.
Sources of Threat Intelligence
* Open Source: Abuse.ch, AlienVault OTX, ThreatFox, MISP, IBM X-Force Exchange
* Commercial: Recorded Future, Anomali, Intel471, Palo Alto AutoFocus, Flashpoint
* Internal TI: IOC enrichment from past incidents, malware reverse engineering, honeypots
* ISACs: Sector-specific collaboration groups
Common IOCs for Log Matching

Correlation | Link related events across different sources

{  "@timestamp": "2024-12-30T10:15:10.000Z",  "message": "Failed password for admin from 10.0.0.6 port 54321 ssh2",  "log": {    "file": {      "path": "/var/log/auth.log"    }  },  "host": {    "name": "webserver01"  },  "agent": {    "type": "filebeat",    "version": "8.11.0"  }}

Logstash parses and enriches the event:

Step 4: Elasticsearch Indexing
Document stored in index security-events-2024.12.30 with full-text search capabilities.
Step 5: Kibana Visualization
* Discover: Search for event.outcome: failure AND service.name: sshd
* Dashboard: View failed login trend over time
* Alert: Trigger if > 5 failed logins from same IP in 5 minutes

Foundations of Log Analysis for Cyber Defense - 5.2 Creating Queries in Elasticsearch and Kibana
Lesson 02: Creating Queries in Elasticsearch and Kibana
Overview
Effective threat hunting and incident investigation require mastery of query languages. This lesson covers the two primary query languages used in the ELK Stack: Kibana Query Language (KQL) and Lucene Query Syntax.
Kibana Query Language (KQL)
KQL is the default query language in Kibana. It is designed to be simple and intuitive for searching log data.
Basic Syntax
field: valuefield: "exact phrase"field: value*           # Wildcardfield > value           # Comparison operatorsfield: value AND field2: value2field: value OR field2: value2NOT field: value
Field Queries
Exact Match:
event.action: "login"user.name: "admin"source.ip: "192.168.1.100"destination.port: 22
Wildcards:
# Prefix matchuser.name: admin*# Suffix matchfile.name: *.exe# Containsmessage: *failed*# Single characteruser.name: admi?
Comparison Operators:
# Greater thandestination.port > 1024# Less thanevent.severity < 3# Greater than or equalhttp.response.status_code >= 400# Less than or equalevent.duration <= 5000# Range (inclusive)destination.port >= 20 AND destination.port <= 25
Boolean Operators
# AND - both conditions must matchevent.outcome: failure AND user.name: admin# OR - either condition matchessource.ip: 10.0.0.5 OR source.ip: 10.0.0.6# NOT - exclude matchesevent.action: login AND NOT event.outcome: success# Parentheses for grouping(event.action: login OR event.action: logout) AND user.name: admin
Nested Field Queries
For nested objects in documents:
# Query nested fields with dot notationsource.geo.country_name: "China"process.parent.name: "cmd.exe"threat.indicator.ip: "203.0.113.50"
Exists Queries
Check if a field exists in the document:
# Field existsuser.name: *# Field does not exist (use NOT)NOT user.name: *
Lucene Query Syntax
Lucene is the underlying query language for Elasticsearch. It offers more advanced features than KQL.
Basic Syntax
field:valuefield:"exact phrase"field:val*              # Wildcard prefixfield:*val              # Wildcard suffixfield:va?ue             # Single char wildcardfield:[min TO max]      # Range query+field:value            # Must match-field:value            # Must not match
Range Queries
# Inclusive range (includes boundaries)destination.port:[1 TO 1024]# Exclusive range (excludes boundaries)destination.port:{1 TO 1024}# Mixed rangedestination.port:[1 TO 1024}    # >= 1 AND < 1024# Open-ended rangesevent.severity:[3 TO *]         # >= 3@timestamp:[2024-01-01 TO *]    # From date onwardsdestination.port:[* TO 1024]    # <= 1024
Fuzzy Searches
Find similar terms (useful for typos or variations):
# Default fuzziness (edit distance of 2)user.name:admni~# Specify edit distance (0, 1, or 2)user.name:admni~1# Similarity for phrasesmessage:"failed login"~3    # Words can be up to 3 positions apart
Proximity Searches
Find terms within a specified distance:
# Words within 5 words of each othermessage:"password failed"~5# Useful for log messagesmessage:"authentication error"~10
Boosting
Increase the relevance score of certain terms:
# Boost a term (default boost is 1)event.action:login^2 OR event.action:logout# Higher boost = more relevantsource.ip:10.0.0.6^5 OR source.ip:*
Regular Expressions
# Regex pattern (enclosed in forward slashes)user.name:/admin[0-9]+/# Match IP patternsource.ip:/192\.168\.1\.[0-9]+/# Match file extensionsfile.name:/.*\.(exe|dll|bat)/
Boolean Operators in Lucene
# AND (both must match)event.action:login AND event.outcome:failure# OR (either matches)source.ip:10.0.0.5 OR source.ip:10.0.0.6# NOT (exclude)event.action:login AND NOT user.name:admin# Required (+) and prohibited (-)+event.action:login -event.outcome:success# Grouping(event.action:login OR event.action:logout) AND user.name:admin
Elasticsearch Query DSL
For complex queries, especially in API calls or detection rules, use Elasticsearch Query DSL (JSON format).
Match Query
{  "query": {    "match": {      "message": "failed password"    }  }}
Term Query (Exact Match)
{  "query": {    "term": {      "event.outcome": "failure"    }  }}
Bool Query (Complex Logic)
{  "query": {    "bool": {      "must": [        { "term": { "event.action": "login" } },        { "term": { "event.outcome": "failure" } }      ],      "should": [        { "term": { "user.name": "admin" } },        { "term": { "user.name": "root" } }      ],      "must_not": [        { "term": { "source.ip": "192.168.1.1" } }      ],      "filter": [        { "range": { "@timestamp": { "gte": "now-1h" } } }      ],      "minimum_should_match": 1    }  }}
Range Query
{  "query": {    "range": {      "@timestamp": {        "gte": "2024-01-15T00:00:00",        "lte": "2024-01-15T23:59:59",        "format": "strict_date_optional_time"      }    }  }}
Wildcard Query
{  "query": {    "wildcard": {      "user.name": {        "value": "admin*"      }    }  }}
Aggregations
Count events by field values:
{  "size": 0,  "aggs": {    "top_source_ips": {      "terms": {        "field": "source.ip",        "size": 10      }    },    "events_over_time": {      "date_histogram": {        "field": "@timestamp",        "calendar_interval": "hour"      }    }  }}
Security-Focused Query Examples
Authentication Attacks
Failed Logins:
event.category: authentication AND event.outcome: failure
Brute Force Detection (multiple failures from same IP):
event.category: authentication AND event.outcome: failure AND source.ip: 10.0.0.6
Successful Login After Multiple Failures:
event.category: authentication AND event.outcome: success AND source.ip: 10.0.0.6
Login Outside Business Hours:
event.action: login AND event.outcome: success
(Then filter by time in Kibana: before 8:00 or after 18:00)
Login from Unusual Location:
event.category: authentication AND NOT source.geo.country_iso_code: US
Network Attacks
Port Scanning Detection:
event.category: network AND event.action: denied AND destination.port < 1024
SSH Brute Force:
destination.port: 22 AND event.outcome: failure
Suspicious Outbound Connections:
network.direction: outbound AND destination.port: (4444 OR 5555 OR 6666 OR 1337)
DNS Tunneling Indicators:
dns.question.type: TXT AND dns.question.name: *.*.*.*.*
Large Data Transfer:
network.bytes > 100000000
Web Application Attacks
SQL Injection Attempts:
url.query: (*SELECT* OR *UNION* OR *INSERT* OR *DROP* OR *UPDATE* OR *DELETE*)
XSS Attempts:
url.query: (*<script>* OR *javascript:* OR *onerror=*)
Directory Traversal:
url.path: (*../* OR *..../* OR *%2e%2e%2f*)
Web Shell Detection:
url.path: (*.php* OR *.asp* OR *.jsp*) AND http.request.method: POST AND http.response.status_code: 200
404 Scanning:
http.response.status_code: 404 AND source.ip: 10.0.0.6
Endpoint Attacks
Suspicious Process Execution:
process.name: (powershell.exe OR cmd.exe OR wscript.exe OR cscript.exe) AND process.command_line: (*-enc* OR *-encoded* OR *hidden* OR *bypass*)
Privilege Escalation:
event.action: "added-member-to-group" AND group.name: (Administrators OR "Domain Admins")
Suspicious File Creation:
event.category: file AND event.action: creation AND file.extension: (exe OR dll OR bat OR ps1) AND file.path: (*\\Temp\\* OR *\\AppData\\*)
Registry Persistence:
registry.path: (*\\Run\\* OR *\\RunOnce\\* OR *\\Services\\*)
Cloud Security
AWS Unauthorized Access:
cloud.provider: aws AND event.action: ConsoleLogin AND event.outcome: failure
Azure Suspicious Activity:
cloud.provider: azure AND event.action: "Add member to role" AND azure.activitylogs.properties.targetResources.role: "Owner"
S3 Bucket Made Public:
cloud.provider: aws AND event.action: PutBucketPolicy AND aws.cloudtrail.request_parameters: *public*
Query Optimization Tips
1. Use Specific Fields
Slow:
*failed*
Fast:
event.outcome: failure
2. Avoid Leading Wildcards
Slow:
message: *password*
Fast:
message: password*
3. Use Keyword Fields for Exact Matches
# For exact match, use .keyword suffixuser.name.keyword: "admin"
4. Limit Time Range
Always specify a time range to reduce the data scanned:
# In Kibana, set time picker to relevant period# In Query DSL, use range filter on @timestamp
5. Use Filters Instead of Queries
Filters are cached and faster for repeated searches:
{  "query": {    "bool": {      "filter": [        { "term": { "event.category": "authentication" } },        { "term": { "event.outcome": "failure" } }      ]    }  }}

* User IP: 192.168.1.1
* Event Time: Around 10:07:30

Scenario 3: Blocked Malicious Activity / Brute-Force attempt
* Attacker IP: 10.0.0.6
* Target: admin user account, various admin pages.
* Access Log (access.log):
